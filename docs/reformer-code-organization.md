# Организация кода форм на @reformer — рекомендации

Документ собран по итогам практической работы, а не из общих соображений. За основу взят перенос
большой формы (кредитная заявка: 6 шагов, ~60 полей, три массива вложенных форм, асинхронная загрузка
черновика и справочников) из примера на `@reformer/ui-kit` в проект на `@kaspersky/hexa-ui` —
с сохранением той же JSON-схемы и последующей проверкой 89 сценариями в реальном браузере.

Всё, что ниже, подкреплено конкретным инцидентом: где мы споткнулись, почему это было не видно и что
предотвратило бы ошибку конструктивно. Рекомендации разделены на три адресата:

- **[К] Конвенции** — как раскладывать код в проекте-потребителе; их стоит зафиксировать в доках и
  в шаблоне (`create-reformer-form`).
- **[Б] Библиотека** — что изменить в API, чтобы конвенции не приходилось держать дисциплиной.
- **[Д] Диагностика** — что должно кричать в dev вместо тишины.

## 1. Раскладка файлов формы

К этой раскладке мы пришли эмпирически, и она себя оправдала на всех трёх формах — от двух полей до
шестидесяти. Роль модуля стоит в **имени файла**, а не в папке:

```
pages/credit-application/
  form.json           layout: только структура и пропы, ни одного правила и ни одной функции
  form.types.ts       форма данных (интерфейсы)
  form.model.ts       initial-значения + фабрики пустых элементов массивов
  form.validation.ts  правила над МОДЕЛЬЮ, разложенные по шагам
  form.behavior.ts    реактивность модели: compute / copyFrom / enableWhen / onChange
  ui.behavior.ts      render-behavior: видимость, инъекция рантайма в узлы, submit, навигация
  form.selectors.ts   якоря схемы как union-тип
  components.tsx      витринные блоки, которые схема зовёт по имени
  constants.ts        словари для `$dataSource(...)`
  api.ts              запросы (форма ответа стабильна: `{ data, status }`)
  Form.tsx            только сборка и разметка страницы
```

**[К] Правило именования.** `form.*` — всё, что описывает саму форму; `ui.*` — всё, что описывает её
поведение на экране. Мы начинали с `behavior.ts` и `ui.ts` и регулярно путались, какой из двух
behavior имеется в виду в разговоре: они разные по слою (модель против дерева рендера), но не по имени.

**[Б] Шаблон.** Эту раскладку стоит генерировать: `npx create-reformer-form credit-application`
создаёт девять файлов с осмысленными заглушками и шпаргаткой в комментариях. Мы фактически
переписывали её руками трижды.

## 2. Границы слоёв: что куда не должно попадать

Главная ценность архитектуры `@reformer` проявилась в момент, ради которого всё затевалось: **схему
удалось перенести на другой UI-Kit, не тронув ни одного узла**. Байт-в-байт та же `form.json`
отрисовалась hexa-ui вместо ui-kit — подменили только реестр. Это работает ровно потому, что слои
разделены строго. Поэтому границы стоит защищать явно:

| Слой | Что внутри | Чего внутри быть не должно |
|---|---|---|
| `form.json` | структура, `componentProps`, `selector` | правила, функции, рантайм-сущности |
| `form.validation` | правила над сигналами модели | React, UI-kit, пропы компонентов |
| `form.behavior` | связи между полями модели | обращения к дереву рендера |
| `ui.behavior` | видимость, patchProps, события, lifecycle | бизнес-правила и расчёты |
| `libs/<kit>` | мост: реестр, адаптеры, обёртки | знание о конкретной форме |

**[К] Проверяемо, а не на словах.** Границу «валидация не знает про UI» легко удержать простым
lint-правилом: `form.validation.ts` не должен импортировать ничего из `react` и из папки моста.

**[К] Инцидент.** Единственное место, где нам пришлось нарушить границу — общий реестр моста, куда по
просьбе владельца переехали витринные блоки конкретной страницы. Через один коммит это дало
`libs → pages` и цикл импортов через барель, который пришлось разрывать пофайловым импортом.
Вывод для доков: **реестр уровня страницы — это нормально и должно быть дефолтом**; общий реестр —
только для того, что переиспользуется формами.

## 3. Мост к дизайн-системе — отдельный слой первого класса

`@reformer` не навязывает UI-kit, и это правильно. Но написание моста сейчас — фольклор: мы вывели
его правила на собственных ошибках. Их стоит либо задокументировать, либо (лучше) сделать
ненужными.

### 3.1 Адаптер требуется почти всем — и это ошибка дизайна

**Инцидент.** Из шести контролов моста четыре имеют адаптер вида `{ strip: ['label'] }` плюс мелкая
нормализация пустого значения. Адаптер заводится не ради перевода диалекта, а ради того, чтобы
рендерер **не подмешал в контрол проп `control`** (ноду формы), который иначе утекает в DOM.

**[Б] Предложение.** Нода формы должна передаваться контролу только по явному запросу:

```ts
interface FieldAdapter {
  /** Передавать ли ноду формы в контрол. По умолчанию — нет. */
  passControl?: boolean;
}
// либо статикой на компоненте, чтобы не ломать ui-kit-поля:
MyField.reformerNeedsControl = true;
```

Тогда адаптер останется только там, где действительно расходятся диалекты: `checked` + DOM-событие у
чекбокса, `fileList` у аплоадера.

### 3.2 Рантайм-пропы теряются, если у контрола есть адаптер

**Инцидент, стоивший дольше всего.** `updateComponentProps({ options })` пишет в **ноду формы**, а
рендерер спредит в контрол пропы **из схемы**. При наличии адаптера нода до контрола не доходит —
обновление исчезает. Практически: селект «модель автомобиля» оставался пустым, хотя загрузка опций по
марке отрабатывала. Чинить пришлось в приложении — сделать один контрол намеренно **без** адаптера,
чтобы он получил ноду и прочитал `componentProps` реактивно.

**[Б] Предложение.** Мержить реактивные пропы ноды поверх схемных в самом рендерере, до применения
адаптера:

```ts
const props = { ...node.componentProps, ...useFormControl(fieldNode).componentProps };
// приоритет: схема — дефолт, updateComponentProps — переопределение
```

Это чинит класс ошибок, а не один случай: любой мост под любой UI-kit наступает на него одинаково.

### 3.3 Контейнеры получают служебные пропы

Контейнерным компонентам рендерер передаёт `selector` строкой (плюс `ref` и колбэки из
`onComponentEvent`). Каждая обёртка обязана его снять, иначе React ругается на неизвестный атрибут.

**[К]/[Б]** Либо задокументировать как контракт («контейнер обязан снять `selector`»), либо не
передавать его вовсе: узел адресуется схемой, компоненту он не нужен.

### 3.4 Одна таблица контролов вместо двух списков

**[К] Конвенция, которая себя оправдала.** Имя в реестре и адаптер — это две обязанности одного
контрола, и держать их в двух местах значит регулярно забывать вторую:

```ts
const CONTROLS = [
  control('Textbox', HexaInput, INPUT_ADAPTER),
  control('Select',  HexaSelect, NO_ADAPTER),  // осознанно без адаптера — ему нужна нода
];
// одна таблица кормит и reg.component, и карту resolveFieldAdapter
```

Третий аргумент **обязателен**: необязательный воспроизвёл бы ровно ту ошибку, от которой защищаемся.

## 4. Связи между файлами: сделать их проверяемыми

Это, на наш взгляд, главный источник ощущения хрупкости. Файлы формы связаны **строками**, и почти
все связи ломаются молча.

| Связь | Между чем | Что происходит при опечатке |
|---|---|---|
| `selector` | `form.json` ↔ `schema.node(...)` | тихо ничего; заметно только при клике |
| `$model(path)` | `form.json` ↔ интерфейс формы | `console.warn`, поле не отрисовано |
| `$dataSource(NAME)` | `form.json` ↔ реестр | без `validateSchema` строка уезжает в проп значением |
| `$component(Name)` | `form.json` ↔ реестр | **бросает** — единственная громкая связь |
| номер шага | визард ↔ массив правил | новый шаг валидируется «успешно» |
| `initialValue` | `form.json` ↔ форма элемента модели | у элемента нет сигналов, поля не рендерятся |

**[К] Что помогает сегодня.** Якоря схемы выносятся в union-тип, и обращение к узлу идёт через
сужающий хелпер — опечатка становится ошибкой компиляции:

```ts
export const SELECTORS = ['wizard', 'promo-card', 'mortgage-section'] as const;
export type PageSelector = (typeof SELECTORS)[number];
```

Список стоит **генерировать из схемы** на билде, иначе он сам становится ещё одной связью по
договорённости.

**[Б] Что решило бы вопрос в корне** — типизировать операторы по форме модели:

```ts
type ModelOp<T> = `$model(${Path<T>})`;
export function defineJsonSchema<T>(schema: JsonFormSchema<T>): JsonFormSchema<T>;
```

Побочно исчезает `as unknown as JsonFormSchema`, который сейчас пишется в каждой странице. Для схемы,
приходящей строкой с сервера, остаётся текущий нетипизированный путь — и это хорошо, что два сценария
выглядят в коде по-разному.

## 5. Визарды: контракт шага должен быть в библиотеке

**Инцидент.** Мост под hexa-ui разошёлся с cdk-шным `FormWizard` по всем трём пунктам: нумерация
шагов (0-based против 1-based), место вызова пошаговой валидации и способ отдать значения в submit
(`onFinish()` без аргументов против `onSubmit(values)`). Каждый пункт пришлось решать заново.

**[Б] Предложение.** Описать шаг как узел со своим селектором и правилами, а нумерацию оставить
деталью реализации моста:

```ts
interface WizardStepContract<T> {
  selector: string;
  validate?: (ctx: { model: FormModel<T>; form: FormProxy<T> }) => boolean | Promise<boolean>;
}
```

Тогда мост под любой UI-kit реализует ровно одно: «покажи шаг N, спроси разрешение на переход».

**[К] Пока этого нет** — адресовать шаги селектором на стороне приложения:

```ts
export const creditValidation = defineSteps<Root, CreditSelector>({
  steps: { loan: step1, applicant: step2, /* … */ confirm: noStepRules },
  extras: crossFieldRules,
});
```

Ключ — тот же `selector`, что у ноды `$component(Step)`; шаг без правил объявляется явно, а не
получается по умолчанию.

## 6. Валидация: `touched` не должен быть ритуалом

**Инцидент, повторившийся дважды.** `shouldShowError = invalid && (touched || dirty)`. Пошаговая
валидация отрабатывает, ошибки проставляются в ноды — и пользователь видит **неработающую кнопку**:
переход заблокирован, подсветки нет. Оба раза мы ловили это уже в браузере.

**[Б] Предложение.**

```ts
validateModel(model, schema, { touch: true })
```

Причём помечать не всю форму (как вынуждено делает приложение сейчас — из-за чего следующий шаг
показывается «тронутым» до ввода), а именно поля, которые схема проверяла.

**[К] Пока этого нет** — прятать `markAsTouched()` внутрь общего хелпера пошаговой валидации, чтобы
забыть его было негде.

## 7. Обвязка страницы

Постоянная стоимость входа сейчас не зависит от размера формы: простая форма из двух полей заняла
340 строк, из которых ~120 — обвязка, дословно повторяющаяся на каждой странице.

**[Б] Схема должна передаваться один раз.** Сейчас она идёт и в `convertJsonToM1Tree` (для сборки
формы), и пропом в `JsonFormRenderer` (для рендера) — две передачи одного артефакта, ничем не
связанные:

```ts
export function createJsonForm<T>(cfg: {
  schema: JsonFormSchema<T>; registry: ComponentRegistry;
  initial: T; behavior?: FormBehaviorFn<T>;
}): { model: FormModel<T>; form: FormProxy<T>; schema: JsonFormSchema<T> };

<JsonFormRenderer form={jsonForm} renderBehavior={…} />
```

Это же место — естественный дом для требования «собрать ровно один раз», которое сейчас держится на
комментарии в прикладном коде.

**[К] Пока этого нет** — один хук на проект (`useJsonForm`), который прячет сборку, мемоизацию и каст.
Честное замечание из нашего опыта: **на трёх формах такой хук не окупается по строкам** (177 строк
общего кода против 36 сэкономленных). Он окупается тем, что требования корректности перестают быть
устной традицией, и начинает окупаться по объёму с четвёртой-пятой формы.

**[Б] Мелочь с большим эффектом.** Модель и форму нельзя пересоздавать между рендерами, иначе форма
теряет введённое. `useMemo` для этого формально не годится — React вправе сбросить кэш; корректная
форма — ленивый инициализатор `useState`. Это стоит либо написать в доках жирным, либо дать готовый
хук в `@reformer/cdk`.

## 8. Диагностика: [Д] один канал вместо тишины

Сейчас сигналы разного качества разбросаны: неизвестный `$component` бросает, неизвестный
`$dataSource` молчит, промах `$model` пишет `warn`, промах `selector` не делает ничего,
нестабильный `renderBehavior` не сообщает о себе никак.

Предлагаем свести в один dev-канал с ссылкой на узел схемы:

| Ситуация | Сейчас | Должно быть |
|---|---|---|
| `schema.node('wizrd')` | тишина | warn: узла нет; список известных селекторов |
| `$dataSource(NAME)` не зарегистрирован | строка уезжает в проп | warn в dev, ошибка в `validateSchema` |
| `$model(path)` без сигнала | `warn` | панель схемы, как у `validateSchema` |
| `renderBehavior` сменил идентичность | тишина | warn: дерево пересобирается каждый рендер |
| у контрола нет адаптера, а он сырой | React-варнинги в DOM | warn с именем компонента |
| `initialValue` не совпал с формой элемента | элемент без сигналов | warn со списком недостающих ключей |

Отдельно: **`validateSchema` стоит включать не только в dev**. Сейчас при битой схеме в проде
`convertJsonToM1Tree` бросает раньше рендера, и пользователь видит белый экран вместо панели ошибок.

## 9. Приоритеты для библиотеки

Порядок — по отношению «выигрыш / размер правки»; первые три дают больше всего и почти ничего не
ломают.

| # | Правка | Пакет | Размер | Ломающее |
|---|---|---|---|---|
| 1 | рантайм-пропы ноды доезжают до контрола (§3.2) | renderer-react | S | почти нет |
| 2 | `validateModel(…, { touch })` (§6) | core | S | нет |
| 3 | громкий промах селектора и прочая диагностика (§8) | renderer-react | S | нет |
| 4 | `control` только по запросу (§3.1) | renderer-react | M | да, смягчаемо статикой |
| 5 | типизированные `$model`/схема (§4) | renderer-json | M | нет (аддитивно) |
| 6 | `createJsonForm` — схема один раз (§7) | renderer-json | M | нет (аддитивно) |
| 7 | контракт шага визарда (§5) | cdk | L | нет |
| 8 | `initialValue` выводится из модели (§4) | renderer-json | S | нет |

## 10. Чек-лист ревью формы

Короткий список, которым удобно проверять чужую форму за пять минут:

- [ ] в `form.json` нет функций и рантайм-сущностей — только структура и пропы;
- [ ] у каждого узла, который адресует поведение, есть `selector`, и он в union-типе страницы;
- [ ] правила валидации не импортируют React и мост;
- [ ] пошаговая валидация помечает поля `touched` — иначе блокировка перехода невидима;
- [ ] скрытие секции (`hideWhen`) идёт в паре с отключением/сбросом полей в `form.behavior` — иначе
      скрытое поле продолжает валидироваться и уезжает в payload;
- [ ] предикаты `hideWhen` читают сигнал целиком (`form.x.value.value`), иначе они не реактивны;
- [ ] `renderBehavior` стабилен по ссылке;
- [ ] у каждого контрола в реестре есть адаптер либо явная пометка, что он не нужен;
- [ ] `initialValue` массива содержит **все** поля элемента;
- [ ] `validateSchema` включён хотя бы в dev.

## Приложение: контекст, на котором сделаны выводы

- Перенесена форма `complex-multy-step-form-renderer-json` из `react-playground`: 157 узлов схемы,
  22 имени компонентов, 12 якорей поведения, 3 массива, 8 вычисляемых полей.
- Схема сохранена без изменений структуры; заменён только реестр — это и подтвердило, что слои
  разделены верно.
- Проверка: `validateFormSchema`, SSR-рендер всех шагов, затем 89 сценариев в Chromium — включая
  прохождение формы до успешной отправки и адаптив на пяти ширинах.
- Два дефекта моста нашлись только живым прогоном, оба — из-за расхождения контрактов, описанного в
  §3: числовые поля не принимали ввод (границы из схемы работали как фильтр клавиш), и селект не
  сбрасывался программно (пустое значение как `undefined` подменялось внутренним состоянием
  дизайн-системы).
